# Запуск УДО через GitHub + Cloudflare Workers

1. У Cloudflare створіть D1 database `udo-db`. Скопіюйте Database ID.
2. R2 не потрібне: докази додаються посиланнями ImgBB.
3. Workers & Pages → Create application → Import a repository → `Crowsk1ck/UDO`.
4. Назва Worker: `udo-panel`; production branch: `main`.
5. Build command: `npm run build:cloudflare`.
6. Deploy command: `npm run deploy:cloudflare`.
7. У build variables додайте `CF_D1_DATABASE_ID` з кроку 1.
8. Для build token потрібні права Workers Scripts Edit та D1 Edit у цьому акаунті. Токен зберігайте лише в Cloudflare, не в репозиторії або чаті.
9. Після першого розгортання у Worker → Settings → Variables and Secrets додайте секрет `UDO_ADMIN_PASSWORD` — унікальний ASCII-пароль щонайменше 16 символів. Збережіть і застосуйте зміни.
10. Відкрийте адресу Worker. Логін: `admin`; пароль: значення секрету. За відсутності секрету вхід керівника повертає 503.

Вхід відбувається через форму `/login`. Існуючий секрет `UDO_ADMIN_PASSWORD` залишається паролем керівника. Використовуйте HTTPS: cookie сесії має Secure, HttpOnly, SameSite=Strict і діє 12 годин. Доступ перевіряється сервером для кожного запиту.

### Доступ співробітників

1. Увійдіть як `admin` зі своїм чинним паролем.
2. Створіть особову справу в розділі «Особовий склад».
3. Відкрийте «Акаунти», виберіть співробітника, задайте унікальний логін та пароль від 16 символів.
4. Передайте співробітнику адресу сайту, його логін і пароль приватно. Пароль керівника не передавайте.
5. Співробітник бачить свою особову справу, свої картки підвищень і рапорти та спільні службові довідники. Може подати рапорт, заповнити свій чекліст і додати ImgBB-докази. Погодження та управління даними доступні керівнику.
6. У «Акаунтах» керівник може заблокувати доступ або встановити новий пароль. Обидві дії завершують поточні сесії співробітника.

Паролі співробітників зберігаються як PBKDF2-хеші з окремими випадковими солями. Відкритої реєстрації немає. Міграція `0001_accounts.sql` застосовується автоматично командою розгортання; наявні записи панелі зберігаються.

Міграції D1 застосовуються перед публікацією. Подальші зміни `main` запускають Workers Builds, якщо Git-інтеграцію увімкнено. Робочі записи Sites автоматично не переносяться: нова база починає роботу з порожнього реєстру.

## Докази ImgBB

У картці вставте HTTPS-посилання `i.ibb.co` (прев’ю) або `ibb.co` (сторінка перегляду), натисніть «Додати посилання» та збережіть картку. Можна додати кілька доказів і відкріплювати їх. База зберігає лише посилання. API-ключ ImgBB не потрібен. Пароль панелі не захищає зовнішні зображення; їхня доступність залежить від ImgBB. Старі вкладення R2 потрібно замінити посиланнями перед збереженням записів.
